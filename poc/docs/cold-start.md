# Cold start

Generated by `make bench` (`bench/coldstart.py`), N=50 runs per row after one
discarded warm-up run. Seconds. Percentiles are nearest-rank.

*create* = `docker run` + (proxied only) network attach, IP lookup and
registry write. *first exec* = `docker exec … true`. *total* = both. Each run
is a fresh sandbox and work dir. The image is already local: **no image pull
is included**.

## What this does and does not say

- **Where it ran:** a Linux VM with Docker Engine 29.9.3 (runc, 4 vCPU), not
  Docker Desktop on a Mac. Docker Desktop adds a VM boundary and file-sharing
  layer, so expect different absolute numbers there; run `make bench` on your
  machine for the figures that matter to you.
- **Pandoc made no measurable difference.** The two images differ by 185 MB on
  disk (370 MB vs 185 MB), but with the image already local, start time is
  the same within run-to-run noise (the p50s differ by under 20 ms and not in
  a consistent direction). Image size would matter for a **pull** onto a new
  node, which was not measured.
- **The proxied path costs about 30–60 ms more to create** (network attach,
  IP lookup, registry write): p50 create 0.133 → 0.191 s with pandoc.
- **A fresh sandbox is ready in about a quarter to a third of a second at
  p50.** That is a floor for a *warm-ish local* start, not a cluster number:
  no Kubernetes scheduling, image pull, or node cold start is in it.
- Because a sandbox is reused for the rest of a session (D2), this cost is
  paid once per session that runs code, not per command. Per-command `exec`
  overhead was not measured separately; "first exec" (~0.115 s p50) is the
  closest figure.
