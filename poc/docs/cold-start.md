# Cold start

Generated by `make bench` (`bench/coldstart.py`), N=50 runs per row after one
discarded warm-up run. Seconds. Percentiles are nearest-rank.

*create* = `docker run` + (proxied only) creating the sandbox's own network,
attaching the proxy to it, IP lookup and registry write. *first exec* =
`docker exec … true`. *total* = create + first exec. *stop* = kill, wait until
the container is gone, remove the network; it is **not** part of cold start,
but it decides how quickly a slot can be reused. Each run is a fresh sandbox
and work dir. The image is already local: **no image pull is included**.

## What this does and does not say

- **Where it ran:** a Linux VM with Docker Engine 29.9.3 (runc, 4 vCPU), not
  Docker Desktop on a Mac. Docker Desktop adds a VM boundary and file-sharing
  layer, so expect different absolute numbers there; run `make bench` on your
  machine for the figures that matter to you.
- **Run-to-run variation is about 10%.** An earlier full run of the same
  benchmark gave a proxied total p50 of 0.33–0.34 s against 0.36 s here. Read
  the figures as "about a third of a second", not as three significant digits.
- **Pandoc made no measurable difference.** The two images differ by 185 MB on
  disk (370 MB vs 185 MB), but with the image already local, start time is the
  same within noise (p50 totals differ by 15 ms or less, in different
  directions across the rows). Image size would matter for a **pull** onto a
  new node, which was not measured.
- **Giving each sandbox its own network costs time.** Proxied create is about
  0.25 s against about 0.13–0.14 s without the proxy (roughly 110 ms more), and
  proxied **stop** is about 0.35 s against about 0.08 s, because it removes the
  network. The shared-network design this replaced was faster, and let one
  tenant's sandbox reach another's (see design-choices D10).
- **A fresh proxied sandbox is ready in about 0.36 s at p50 (0.41 s p95)**,
  0.24–0.26 s without the proxy. That is a floor for a warm local start, not a
  cluster number: no Kubernetes scheduling, image pull, or node cold start is
  in it.
- Because a sandbox is reused for the rest of a session (D2), this cost is
  paid once per session that runs code, not per command. Per-command `exec`
  overhead was not measured separately; "first exec" (about 0.115 s p50) is
  the closest figure.
