# Cold start

Generated by `make bench` (`bench/coldstart.py`), N=50 runs per row after one
discarded warm-up run. Seconds. Percentiles are nearest-rank.

*create* = `docker run` + (proxied only) creating the sandbox's own network,
attaching the proxy to it, the registry transaction that fences and claims the
session, IP lookup and registration. *first exec* = `docker exec … true`.
*total* = create + first exec. *stop* = kill, wait until the container is gone,
remove the network; it is **not** part of cold start, but it decides how quickly
a slot can be reused. Each run is a fresh sandbox and work dir. The image is
already local: **no image pull is included**.

## What this does and does not say

- **Where it ran:** a Linux VM with Docker Engine 29.9.3 (runc, 4 vCPU), not
  Docker Desktop on a Mac. Docker Desktop adds a VM boundary and file-sharing
  layer, so expect different absolute numbers there; run `make bench` on your
  machine for the figures that matter to you.
- **Run-to-run variation is about 10%.** Four full runs of this benchmark over
  the course of the work gave a proxied total p50 between 0.33 s and 0.36 s, and
  the code changed between them. Read the figures as "about a third of a
  second", not as three significant digits.
- **Pandoc made no measurable difference.** The two images differ by 185 MB on
  disk (370 MB vs 185 MB), but with the image already local, start time is the
  same within noise (p50 totals differ by 1 ms without the proxy and 9 ms with
  it). Image size would matter for a **pull** onto a new node, which was not
  measured.
- **Giving each sandbox its own network costs time.** Proxied create is about
  0.23 s against about 0.12 s without the proxy (roughly 110 ms more), and
  proxied **stop** is about 0.38 s against about 0.14 s, because it removes the
  network. The shared-network design this replaced was faster, and let one
  tenant's sandbox reach another's (see design-choices D10).
- **A fresh proxied sandbox is ready in about 0.33 s at p50 (0.38 s p95)**,
  about 0.22 s (0.26 s p95) without the proxy. That is a floor for a warm local
  start, not a cluster number: no Kubernetes scheduling, image pull, or node
  cold start is in it.
- Because a sandbox is reused for the rest of a session (D2), this cost is
  paid once per session that runs code, not per command. Per-command `exec`
  overhead was not measured separately; "first exec" (about 0.09-0.115 s p50)
  is the closest figure.
